# 0.2.0: the settings file is `.env.development`

**Rename `.env` to `.env.development`, by hand, then upgrade again.** dbu6 now
reads its settings from `.env.development`, the name Sapporta uses, so every
`sapporta` command finds the app's port there. It no longer reads `.env`, and
every `dbu6` command stops with "`.env` is no longer read; rename it to
`.env.development`" until the file is renamed. `dbu6` never moves the file
itself: it may set `SAPPORTA_DATA_DIR`, and a command that ignored it would
open the wrong database. So this upgrade stops at its migration and rolls back
to the version you had, which still reads `.env`; nothing has changed yet.

In the project folder:

1. In `.gitignore`, replace the `.env` and `.env.agent` lines with `.env*`.
2. `mv .env .env.development`
3. Remove `SAPPORTA_API_URL` from `.env.development`, from `mise.toml` or
   `mise.local.toml`, and from the shell, unless it points somewhere other
   than this project's own port on purpose. It outranks the port, so a stale
   one wins.
4. If the folder has no `sapporta.json`, create one holding `{}`: it is how a
   `sapporta` command finds the project, and so its port.
5. `npx dbu6 upgrade` again.
6. `npx dbu6 agent env`, which rewrites `.env.agent` with the token only.
   Until then the old file still works: dbu6's `sapporta` takes only its
   token.

What changed around it:

- `.env.agent` holds only `SAPPORTA_API_TOKEN`. The `sapporta` command finds
  the app from `SAPPORTA_API_PORT`, in the environment or else in
  `.env.development`, and needs no `SAPPORTA_API_URL` wherever dbu6 sets the
  port.
- For `curl`, the app is at `http://localhost:<SAPPORTA_API_PORT>`; load the
  token with `set -a; . ./.env.agent; set +a`. The prompts dbu6 hands you name
  the app's address themselves.
